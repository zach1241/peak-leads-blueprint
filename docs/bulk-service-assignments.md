# Bulk client service assignments

Owners and admins can assign one or several teammates to an entire client service or generic project. Multiple services across different clients can be selected in one save. This update provides assignment controls only; it does not create services or change deliverables, schedules, quantities, or generation behavior.

The action replaces the selected services' assignees on every unfinished current or upcoming task. Completed and cancelled tasks, and occurrences whose period ended before today in Africa/Johannesburg, retain their assignments. An overdue one-off without a delivery period remains eligible. Counts come from the database rather than the Tasks page's current page or filters.

**Current tasks only** changes eligible existing tasks and leaves saved future defaults alone. **Current tasks and future occurrences** also stores an independent default for each selected client service/project and replaces that project's known deliverable and manual series defaults. Selecting no teammates deliberately unassigns eligible work and, with future scope, saves an empty default. The transaction validates every selected project and teammate before writing; invalid selections cannot partially update a service.

Future service occurrences choose a saved deliverable rule first, then the client service/project default. A saved empty rule counts as an intentional individual override and prevents fallback. For manual children the saved root rule wins, followed by the project default, followed by the legacy root's assignees if neither default exists. New deliverables without prior occurrences inherit the project default. A new manual repeating task created with explicit assignees captures its explicitly chosen team as its own series rule. Leaving the initial team blank with the task form's default scope inherits the saved project team; selecting future scope with a blank team explicitly creates an unassigned series. Existing task edits retain their previous behavior. Owners/admins can change an individual recurring task afterward to override the bulk default for that deliverable.

## Database API

In the app, open **Tasks → Assign service work**, or open a client and expand **Assign service work**. Choose a client (or **All clients**), select the services/projects, choose teammates, select **Selected work only** or **Selected work and future occurrences**, then save. **Leave unassigned** must be selected explicitly to clear a team's assignments. The preview shows exact eligible task counts; the saved result reports the actual count at save time.

`public.set_service_assignees(p_organization_id uuid, p_project_ids uuid[], p_assignees uuid[], p_apply_to_future boolean)` returns an integer count of eligible tasks matched, including tasks already assigned to those people. It accepts 1–1000 project IDs and up to 100 teammate IDs. Empty teammate lists are allowed, while null arrays, null elements, and null scope are rejected. Duplicates are normalized. Every project and teammate must belong to the workspace, and the caller must be its owner or admin.

`public.service_assignment_options(p_organization_id uuid)` is a read-only, SECURITY INVOKER RPC for workspace members. It returns one row per workspace project: `project_id uuid`, `eligible_tasks bigint`, `default_configured boolean`, and `default_assignees uuid[]` sorted by user ID. The `default_configured` flag distinguishes an absent default from a saved empty default. The app joins these IDs with client/project/service labels.

`service_assignment_rules` has columns `organization_id uuid` and `project_id uuid`, with a compound primary key and compound tenant foreign key to projects. `service_assignment_members` adds `user_id uuid`, with a compound primary key and compound tenant foreign keys to the default rule and workspace membership. Both tables enable RLS and grant authenticated users SELECT only. The private SECURITY DEFINER default helper has an empty search path and repeats caller role, tenant, input, and membership validation. Removing a membership cascades out of saved defaults.

The public assignment RPC remains SECURITY INVOKER. It locks selected projects in UUID order, then eligible task rows in UUID order, before atomically replacing task assignments and saved defaults. It does not update any task fields. Project row locks serialize task generation through the existing project foreign key.

## Rollout and validation

Apply only `supabase/migrations/20261009132621_bulk_service_assignments.sql` after reviewing the hosted schema and migration history. The prior local source `20261006010000_recurring_assignments.sql` corresponds to hosted migration `20261009130346_recurring_assignments`; this known timestamp mapping is not a reason to rerun it. Do not reset the database or rerun imports. The new migration does not backfill or modify existing tasks or assignment defaults and notifies PostgREST to reload its schema.

The hosted rollout on 9 October 2026 applied this source once through the Supabase migration connector, recorded as `20261009133724_bulk_service_assignments`. The connector generates the hosted timestamp. Reconcile these known source/hosted timestamp mappings before a future CLI `db push`; do not reapply either already-installed migration.

`supabase/tests/bulk-service-assignments.sql` contains pure SQL with no psql meta commands. Synthetic users, workspaces, services, and tasks are created inside BEGIN/ROLLBACK. Checks cover assigning 400 tasks at once and 402 tasks across services, multiple clients, shared/single assignments, temporary edits, weekly/monthly/manual inheritance through the generator and normal save RPC, new deliverable fallback, explicit empty overrides, history, done/cancelled work, duplicates, invalid input, role/tenant isolation, direct API writes, tenant foreign keys, membership removal, and anonymous callers. It returns an aggregated `passed_checks` / `all_passed` result before rolling back. Run with the migration already installed, or combine the migration body and suite inside one explicitly authorized rollback preview before hosted rollout.

For the existing local Supabase stack, run `npm run test:bulk-assignees`. `BULK_ASSIGNMENT_TEST_CONTAINER` can select a prepared disposable PostgreSQL container. The runner uses local Docker only and never reads hosted credentials. The full SQL suite can also be run with `psql -v ON_ERROR_STOP=1` against a disposable PostgreSQL database with the repository migrations installed.
